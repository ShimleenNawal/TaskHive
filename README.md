# TaskHive

TaskHive is a full-stack project collaboration application built to demonstrate
secure authentication, role-aware project management, relational data modeling,
and a modern responsive frontend.

The current MVP lets verified users create projects, manage project details and
deadlines, and collaborate with other registered users. Task management is the
next planned module and is not yet implemented.

## Highlights

- Email-verified account registration and JWT-based authentication
- Password hashing with Argon2 and protected API routes
- Project creation, listing, editing, and deletion
- Owner/member roles with owner-only management controls
- Member invitation and removal for verified users
- Responsive React interface with persisted light/dark mode
- PostgreSQL persistence with versioned Alembic migrations
- Docker Compose development environment with MailHog email inspection
- Backend tests for signup, verification, login, token handling, and user access
- Interactive OpenAPI documentation generated by FastAPI

## Architecture

```text
React/Vite client
      |
      | HTTP + Bearer JWT
      v
FastAPI REST API ----> MailHog (development email)
      |
      | SQLAlchemy / Alembic
      v
PostgreSQL
```

The frontend stores the access token in browser local storage and attaches it
to authenticated requests. FastAPI validates the token, resolves the current
user, and applies owner/member authorization at the route layer. Project
membership is represented by a separate join table with a unique
`(project_id, user_id)` constraint.

## Quick start with Docker



### Prerequisites

- Docker Desktop with Docker Compose v2
- Git
- For host-based frontend development: Node.js 20.19+ or 22.12+



### 1. Clone and configure

```bash
git clone https://github.com/ShimleenNawal/TaskHive
cd TaskHive
cp backend/.env.example backend/.env
cp frontend/.env.example frontend/.env
```

Replace `SECRET_KEY` in `backend/.env` with a strong local value. For example:

```bash
python3 -c "import secrets; print(secrets.token_urlsafe(48))"
```

The example database credentials are development-only and match
`docker-compose.yml`.

### 2. Start the application

```bash
docker compose up --build
```

The backend waits for PostgreSQL, applies all Alembic migrations, and then
starts the development server.

### 3. Open the services

- Web application: [http://localhost:5174](http://localhost:5174)
- API documentation: [http://localhost:8000/docs](http://localhost:8000/docs)
- Alternative API documentation: [http://localhost:8000/redoc](http://localhost:8000/redoc)
- Health check: [http://localhost:8000/health](http://localhost:8000/health)
- MailHog inbox: [http://localhost:8025](http://localhost:8025)
- PostgreSQL from the host: `localhost:5433`

Stop the stack with:

```bash
docker compose down
```

To also remove the local database volume and start with empty data:

```bash
docker compose down -v
```



## Reviewer walkthrough

This is the shortest path through the implemented functionality:

1. Start the Docker stack and open the web application.
2. Register the first user.
3. Open MailHog and inspect the TaskHive verification email.
4. Copy the token from the email link and visit
  `http://localhost:8000/api/auth/verify?token=<token>`.
5. Log in and create a project with an optional description and deadline.
6. Register and verify a second user in a separate browser profile.
7. As the first user, open the project and add the second user as a member.
8. Confirm that the owner can edit/delete the project and manage members, while
  the member can view the project but does not receive owner controls.
9. Review API behavior directly in Swagger UI at `/docs`.

The direct API verification step in item 4 is a temporary reviewer workaround:
verification emails currently link to a planned frontend `/verify` route that
has not yet been implemented.

## Local development without full Docker

Use Docker for PostgreSQL and MailHog, then run both application processes on
the host.

### 1. Start dependencies

```bash
docker compose up -d db mailhog
```

Copy `backend/.env.example` to `backend/.env`, then change these hostnames:

```dotenv
DATABASE_URL=postgresql://mlbd:postgres@localhost:5433/taskhive
TEST_DATABASE_URL=postgresql://mlbd:postgres@localhost:5433/taskhive_test
MAIL_SERVER=localhost
```

Keep the remaining variables from `.env.example` and replace `SECRET_KEY`.

### 2. Run the backend

Prerequisites: Python 3.13+ and Poetry 2.

```bash
cd backend
poetry install
poetry run alembic upgrade head
poetry run uvicorn app.main:app --reload
```



### 3. Run the frontend

In another terminal:

```bash
cd frontend
cp .env.example .env.local
npm ci
npm run dev -- --port 5174
```



## Environment configuration

Backend settings are loaded from `backend/.env`.

- `DATABASE_URL`: application PostgreSQL connection string
- `TEST_DATABASE_URL`: isolated PostgreSQL database used by Pytest
- `SECRET_KEY`: private key used to sign JWTs
- `BACKEND_CORS_ORIGINS`: JSON list of allowed browser origins
- `MAIL_SERVER`: SMTP host; `mailhog` in Docker or `localhost` on the host
- `MAIL_PORT`: SMTP port, normally `1025` for MailHog
- `ALGORITHM`: JWT signing algorithm
- `TOKEN_EXPIRE_HOURS`: access-token lifetime
- `VERIFICATION_TOKEN_EXPIRE_HOURS`: email-verification token lifetime

The frontend expects:

- `VITE_API_URL`: API base URL including `/api`, normally
`http://localhost:8000/api`

Never commit `.env` files or production secrets.

## API overview

All application endpoints are under `/api`; authenticated routes require an
`Authorization: Bearer <token>` header.

**Authentication**

- `POST /api/auth/signup` — create an unverified user and send a verification email
- `GET /api/auth/verify?token=...` — verify an email address
- `POST /api/auth/resend-verification` — issue and email a new verification token
- `POST /api/auth/login` — return a JWT for a verified user

**Users**

- `GET /api/users/me` — return the authenticated user
- `GET /api/users/` — list other verified users

**Projects**

- `POST /api/projects` — create a project and OWNER membership
- `GET /api/projects` — list projects visible to the current user
- `GET /api/projects/{project_id}` — return project details and members
- `PATCH /api/projects/{project_id}` — update an owned project
- `DELETE /api/projects/{project_id}` — delete an owned project
- `POST /api/projects/{project_id}/members` — add a verified member
- `DELETE /api/projects/{project_id}/members/{user_id}` — remove a member

FastAPI's `/docs` page is the authoritative, executable request/response
reference.

## Tests and quality checks

The backend test suite uses a separate PostgreSQL database and recreates its
schema for each test.

Create that database once after starting the Compose database:

```bash
docker compose exec db createdb -U mlbd taskhive_test
```

Then, from `backend/` with the host-oriented `.env` values shown above:

```bash
poetry install
poetry run pytest
```

The current automated coverage focuses on authentication and user endpoints.
Project behavior should be reviewed through the UI and interactive API docs
until project endpoint tests are added.

Run frontend checks from `frontend/`:

```bash
npm ci
npm run lint
npm run build
```

## Implementation notes for reviewers

- Authorization is enforced server-side; hiding owner controls in the UI is
only a presentation concern.
- Project deletion cascades to project memberships at the database level.
- Users must verify their email before login or project membership.
- Logout is client-side only; there is no server-side token revocation endpoint.
- Access tokens expire after the configured lifetime; unauthorized frontend
responses clear the local session and return the user to login.
- Authentication uses `VITE_API_URL`, while several project pages still hardcode
`http://localhost:8000/api`.
- The Axios 401 interceptor matches `/api/auth/...`, but auth requests are sent
as `/auth/...` relative to `VITE_API_URL`, so a failed login can currently be
treated like an expired session.
- Alembic migration history captures the user and project schema evolution.
- Docker services use source bind mounts and reload mode for development; the
included container configuration is not a hardened production deployment.
- There is no CI workflow, seed script, or production deployment configuration yet.
- `pyproject.toml` and `poetry.lock` are the backend dependency sources of
truth. `requirements.txt` is retained as a snapshot and may be removed soon.
